## 22:0x-22:5x 公众号注释修正 + 打通 GitHub 推送兜底通道

**注释修正**：`WechatFollow.astro` 顶部注释仍写「扫码 + 搜一搜联合码（type: 'search'）」，而 `site.ts:150` 早已是 `type: 'follow'`（直接关注码）——说明与配置相反，会误导后来人。只改 3 行注释，无逻辑变更、无产物影响（不用重建部署）。

**踩了大坑：GitHub 推送连续失败，根因是分层网络故障**：
- `github.com:443` 整段阻断（`connect=0.000`，TCP 都连不上），但 **`api.github.com` 200 / 0.3s 正常**。
- 环境注入了代理 `http(s)_proxy=http://127.0.0.1:60045`，走代理报 `CONNECT tunnel failed, response 502`；清空代理走直连则 `Connection was reset`。**两种失败要分开判断，别把 502 当成"代理能用"**。
- 还发现 `~/.gitconfig` 里 `url.https://github.com/.insteadOf=git@github.com:`，导致 `git push git@github.com:...` 被悄悄改写成 HTTPS，绕 SSH 的尝试全部无效。

**解决方案（已固化为 `npm run push:api`，脚本 `scripts/push-via-api.mjs`）**：
GitHub Git Data API 逐对象上传 —— `blob → tree(base_tree 必须是**父提交**的 tree，一开始写成新提交自己的 tree 导致 422) → commit → PATCH refs`。逐项校验 blob/tree 哈希与本地一致，非快进则拒绝，远端 tree 已相同则幂等退出。
⚠️ GitHub 会重写 author/committer（给的是 UTC +0000），**远端 commit SHA 必然与本地不同**，实测穷举消息尾换行也无法复刻。所以推完必须 `git fetch origin && git reset --hard origin/master` 让历史收敛——本次已执行，本地现与远端完全重合。

**最终状态**：`d42b3a7`（注释修正，经 API 推送）→ `232868d`（push:api 脚本，走正常 git 通道）。git 通道期间自行恢复，fetch + push 均成功，工作区干净、与 origin/master 无差异。

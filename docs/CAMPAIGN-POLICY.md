# 活动时间管理规范（Campaign Policy）

> 制定：2026-11-03　｜　真源：`src/config/campaigns.ts`　｜　闸门：`npm run check:campaigns`
> 适用对象：教师普惠、WorkBuddy 邀请、任何"限时活动 / 限时优惠 / 限时报名"类内容

---

## 1. 为什么需要一份规范

MokaKit 是**纯静态站**：页面在构建时就已经把 HTML 写死了。这意味着——

- 没有服务端，无法在活动结束的那一刻"自动删掉"页面上的活动卡片；
- 如果把活动结束时间写成注释（改造前的做法：`active: true` + 注释「活动结束（2026-09-30）」），
  就只能靠人记得改代码。教师普惠就是活案例：**9-30 结束，到 11-03 仍 `active: true`**，已过期 34 天。

所以"到期自动下线"必须换算成静态站能执行的三个动作：
**构建期判定 + 发布前闸门 + 重建时限约定**。

---

## 2. 三重保障机制

| 层 | 机制 | 何时生效 | 代码 |
|---|---|---|---|
| ① 构建期判定 | `resolveCampaign()` 判断 `active` + 起止日期，过期即**不渲染**活动块 | 每次 `npm run build` | `src/config/campaigns.ts` |
| ② 发布前闸门 | `check:campaigns` 扫描所有活动，已过期仍开 / 临期 / 未开始都报警 | 每次 `check:all` | `scripts/check-campaigns.mjs` |
| ③ 重建时限 | 活动结束日起 **7 天内必须重新构建并部署**，否则线上仍挂旧内容 | 人工 / 迭代周期 | 本文 §6 |

> 三者缺一不可：① 保证"只要构建，就一定不展示过期活动"；② 保证"过期了会有人知道"；③ 保证"构建真的会发生"。静态站无法做到秒级下线，7 天是承诺上限。

---

## 3. 数据结构

活动统一登记在 `src/config/campaigns.ts` 的 `CAMPAIGNS` 数组：

```ts
{
  id: 'workbuddy-teacher',        // kebab-case 唯一标识，日志/报警用它定位
  name: 'WorkBuddy 教师普惠',      // 展示名
  activityUrl: 'https://...',     // 官方活动页，组件跳转用
  startAt: '2026-09-01',          // 开始日（含），可留空 = 不限
  endAt: '2026-09-30',            // 结束日（含），null = 长期有效
  active: true,                   // 人工总开关，优先级最高
  rulesCheckedAt: '2026-09-01',   // 规则文案最后核对日
  warnDays: 14,                   // 结束前多少天开始提醒
}
```

### 字段语义

| 字段 | 必填 | 语义 | 注意 |
|---|---|---|---|
| `id` | 是 | 唯一标识 | 改动会让报警历史断档 |
| `startAt` | 否 | 开始日，含当天 | 未到开始日 → `not-started`，不展示 |
| `endAt` | 否 | 结束日，含当天；`null` = 长期 | **不要用注释写结束日期**，写进这个字段 |
| `active` | 是 | 人工开关 | `false` 优先级最高，用于提前下线 |
| `rulesCheckedAt` | 否 | 规则核对日 | 月度复核时更新 |
| `warnDays` | 否 | 临期提醒阈值 | 默认 14 天 |

### 判定顺序

```
active === false          → disabled     不展示
today < startAt           → not-started  不展示
today > endAt             → expired      不展示（自动下线）
否则                       → active / long-term  展示
```

日期一律按**本地时区**取当天（不是 UTC），避免东八区凌晨判错一天。
测试时可用 `CAMPAIGN_TODAY=2026-09-15` 模拟任意日期，不必改系统时间。

## 4. 新增一个活动的 SOP

1. **登记**：在 `src/config/campaigns.ts` 的 `CAMPAIGNS` 加一条，填 `id / name / startAt / endAt / active`。
   `endAt` 必须来自官方活动页的明确日期；官方没写截止就填 `null`（长期），**不要猜**。
2. **接入**：`site.ts` 用 `byId('<id>')` 取值；组件读派生出的 `live` 字段（如 `WORKBUDDY.teacherLive`），
   **不要直接读 `active`** —— 那只是人工开关，不含时间窗。
3. **文案合规**：活动块内必须写清"以官方活动页为准"，限时/限量的表述不得承诺具体数值。
4. **闸门**：`npm run check:campaigns`，确认新活动状态符合预期（未开始 / 有效 / 已禁用）。
5. **构建**：`npm run build`，抽查活动块是否按预期出现或消失。
6. **记录**：在 changelog 的 notes 里写一句"新增活动 X（起止）"。

---

## 5. 到期后怎么办（决策树）

活动到期时，`check:campaigns` 会报警。三选一，**必须选一个并落到代码**：

```
活动到期（expired）
├─ 官方已续期 → 把 endAt 改成新日期，rulesCheckedAt 更新为今天
├─ 官方已结束 → active 置 false（保留记录，便于明年复用）
└─ 换成新活动 → 旧活动 active:false，新增一条新 id（不要复用 id）
```

**不要做的事**：

| 反模式 | 后果 |
|---|---|
| 只改注释、不改 `endAt` | 下一个人继续被误导（本次事故根因） |
| 直接删掉登记项 | 失去"办过什么活动"的历史，也无法解释流量波动 |
| 复用旧 `id` | 报警与日志无法区分两届活动 |
| 把 `endAt` 写成 `null` 逃避过期 | 活动永久挂着，等于没有管理 |

## 6. 时限与复核节奏

| 周期 | 动作 | 责任 |
|---|---|---|
| 每次构建前 | `check:campaigns` 随 `check:all` 自动跑 | 自动 |
| 活动期内每月 | 复核官方规则与日期，更新 `rulesCheckedAt` | 人工（月度维护窗口） |
| 活动结束后 **7 天内** | 重新构建并部署，确保线上不再展示 | 人工（硬性 SLA） |
| 每季度 | 清理 `active:false` 且已结束超过 1 年的活动登记 | 人工 |

### 已知局限（必须知道）

- **构建完成后活动不会自己消失**。若活动 9-30 结束、下次构建在 10-20，则 9-30 到 10-20 之间线上仍展示。
  这是静态站的物理限制，靠 §6 的 7 天 SLA 兜住。
- 因此**短期活动（< 1 个月）不要依赖"自动下线"就不管**，应在活动结束当天安排一次构建。
- 若未来接入定时构建（cron 重建），可把 SLA 从 7 天压到 1 天；当前未接入。

> 教师普惠的最终处理：**保留记录与日期，把 `active` 置 false**。
> 理由有两条：① 每次 `check:campaigns` 都报"过期但未关"会造成警报疲劳，人一旦习惯性忽略警告，闸门就失效了；
> ② 保留 `endAt` 与文案，明年教师节只需 `active: true` + 改两个日期即可复用，不用重写代码。
> 即使忘了置 false，构建期仍会因 `endAt` 过期而不渲染 —— 这是刻意的双保险。

## 8. 故障排查

| 现象 | 原因 | 处理 |
|---|---|---|
| 活动该展示却没出现 | `active:false` 或今天不在时间窗 | `check:campaigns` 看 reason |
| 活动过期了还在线上 | 构建于活动期内，之后没重建 | 立即重建部署（SLA 内） |
| `check:campaigns` 报 id 重复 | 两条同 id | 改 id，不要复用 |
| 报 `startAt 晚于 endAt` | 日期写反或跨年写错 | 修正日期 |
| 活动在本地正常、线上没有 | 线上是旧产物 | 确认部署是否成功、`/var/www/mokakit` 时间戳 |
